Three Bugs That Taught Me More Than Any Tutorial

Lessons from building Arethos, a mental wellness app where React Native’s abstractions broke down and the real engineering started.

Arethos is a mental wellness app I am building with two teammates for KNUST students. It is not released yet. It has an AI-powered journal, a mood tracker with sleep logging, and a reflections tab that surfaces behavioural patterns. We built it on React Native and Expo SDK 54, backed by SQLite for fully offline-first storage and Groq for fast inference.

The interesting parts aren’t in the feature list. They’re in the three bugs that forced me to understand what React Native actually does underneath, instead of just using it.

Bug 1 — the delete button that didn’t exist

The journal screen shows recent entries as cards. Each card has a three-dot menu. You tap it, a dropdown appears with a “Delete” option. Simple. Except tapping “Delete” did absolutely nothing.

The dropdown was positioned with zIndex: 10. Visually it rendered on top of everything. But React Native’s zIndex only works between direct siblings in the same parent view. Our dropdown and the card’s TouchableOpacity wrapper were not siblings. The dropdown was a child of the card, and the wrapper was intercepting every tap before it could reach the dropdown’s buttons.

This is a fundamental difference from CSS. On the web, z-index creates stacking contexts that govern hit-testing globally. In React Native, touch responders are resolved by the view tree’s parent–child hierarchy, not by visual layering. A child can never escape its parent’s touch boundary through zIndex alone.

The fix: replace the inline dropdown with a Modal bottom-sheet. A Modal renders at the OS level, outside the entire view tree, so nothing can intercept its touches. That isn’t a workaround. It’s the correct pattern for any overlay that needs to receive taps.

Bug 2 — the slider that teleported

The mood screen has a sleep slider: drag a knob across a track to log hours slept. Except sometimes, mid-drag, the knob would snap back to zero. Other times it wouldn’t move at all.

The root cause took a while to find: a stale closure.

PanResponder.create() runs once, inside a useRef, at mount. Every callback it defines captures the variables in scope at that single moment. Those variables are frozen forever. My onPanResponderMove was reading a state variable called value, converting it to a pixel position, and using that as the drag origin. But value inside the closure was always its initial 0.

# THE BUG: value is always 0 inside the frozen closure
onPanResponderMove: (_, gs) => {
  const startPixel = valueToPixel(value);   // value === 0, always
  knobX.setValue(startPixel + gs.dx);
}

# THE FIX: capture the real position into a ref at drag start
const dragStartX = useRef(0);

onPanResponderGrant: (evt) => {
  dragStartX.current = evt.nativeEvent.locationX - KNOB_D / 2;
},
onPanResponderMove: (_, gs) => {
  const newPos = dragStartX.current + gs.dx;   // always correct
  knobX.setValue(Math.max(0, Math.min(newPos, maxWidth)));
}

The lesson is broader than React Native. Any system that creates callbacks at initialisation and reuses them later (event listeners in embedded systems, registered callbacks in game engines, hooks in ML training loops) is vulnerable to stale closures. If a callback needs current state, pass it through a mutable reference, not a captured variable.

Bug 3 — the vibration that took nine iterations

This one wasn’t a bug. It was a design problem that revealed how Android haptics actually work.

We wanted the theme toggle to produce a specific sensation: a subtle shake in the palm. Not a harsh buzz, not a single tap. A gentle multi-pulse tremor.

My first instinct was expo-haptics. On Android none of its presets worked; every one felt like the same single electronic buzz at slightly different intensities. The reason: expo-haptics calls VibrationEffect.createOneShot(duration, amplitude) underneath. One shot, one pulse. You can adjust how hard and how long, but it is always a single impulse.

To get a multi-pulse waveform you need VibrationEffect.createWaveform(), which React Native’s built-in Vibration.vibrate([pattern]) calls. The array alternates wait and vibrate durations in milliseconds.

#ApproachResult
1impactAsync(Medium)Too strong, single buzz
2selectionAsync() × 2, 55 ms gapDoesn’t feel natural
3impactAsync(Light) × 3Still mechanical
4notificationAsync(Error)The wrong-password one
5Vibration.vibrate([0,40,30,40,30,40])Getting there, too strong
6Vibration.vibrate([0,20,30,20,30,20])Better, still heavy
7Vibration.vibrate([0,12,32,12,32,12])Confirmed: subtle palm shake

The key insight: pulse duration controls perceived intensity, not amplitude. A 40 ms pulse feels harsh regardless of what amplitude the OS chooses. A 12 ms pulse barely registers consciously. You feel it in your palm without it interrupting your attention. Three 12 ms pulses with 32 ms of breathing room produce exactly the sensation we wanted.

# src/lib/haptics.js — the entire haptics layer
export function subtleShake() {
  if (Platform.OS === "android") {
    Vibration.vibrate([0, 12, 32, 12, 32, 12]);
  } else {
    Haptics.impactAsync(Haptics.ImpactFeedbackStyle.Light);
  }
}

What these three bugs have in common

Each one forced me past the abstraction layer. React Native presents a clean API (zIndex for layering, state for data, expo-haptics for vibration) but the abstraction leaks in predictable ways when you push on it.

That is the same lesson I keep meeting elsewhere. A library is a compression of someone else’s decisions. It works beautifully until your problem sits outside the compression, and then the only way through is to understand what it was hiding.
